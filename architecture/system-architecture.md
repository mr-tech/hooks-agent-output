## Purpose

Hooks.gg is a Discord message/embed builder: users compose Discord messages in a WYSIWYG editor and send them via webhooks, with a companion Discord bot. The system supports embeds, rich text (Markdown), and Components V2.

The workspace root is `/usr/local/bin/hooks`. It is **not itself a git repository**; it holds four sibling repositories:

| Repo                      | Remote                                  | Branch   | Role                                                        |
| ------------------------- | --------------------------------------- | -------- | ----------------------------------------------------------- |
| `website`                 | `hooks-gg/website`                      | `master` | The product: Next.js app, API, and Discord bot endpoints    |
| `project-utils`           | `hooks-gg/project-utils`                | `master` | Shared data layer: Prisma schema, generated Kysely types    |
| `preview-image-generator` | `hooks-gg/preview-image-generator`      | `prod`   | Headless-browser screenshot service for message previews    |
| `agent-output`            | `mr-tech/hooks-agent-output`            | `master` | Process record for the agent pipeline (its own repo)        |

`hooks.code-workspace` at the root defines the same working set — all four repos — plus two out-of-tree reference clones: `../discord-api-types` (upstream `discordjs/discord-api-types`) and `../embed-generator` (upstream `merlinfuchs/embed-generator`). Both reference clones point at their upstream remotes, not hooks-gg forks; they are consulted, not developed. `website.code-workspace` is a narrower view (website + the two reference clones). Deprecated repos live outside the project space in `/usr/local/bin/hooks-deprecated/`.

## Components

### website (the product)

- **Next.js 16 hybrid**: App Router (`src/app/`) for UI pages (`message/`, `preview/`, `legal/`), Pages Router (`src/pages/api/`) for API endpoints: tRPC (`trpc/`), NextAuth (`auth/`), Discord interactions (`interactions-edge.ts`, `interactions-server.ts`), `cron.ts`, `v1/`, `messages/`. `interactions-edge.ts` alone runs on the edge runtime (`config.runtime: 'edge'`). Production serves Next 16.4.6 from website `master` `d1bb9b0`, released 2026-11-20T08:07:52Z (plan 018; post-deploy row B-7, `verification/018/devops/b7-production-version-read.txt`). `tsconfig.json` `paths` holds only the project's own aliases (`~/*`, `bot/*`), and the bundler reads it as runtime resolution, so a types-only fix never goes there: an entry keyed on a package name replaced highlight.js with its `.d.ts` in the bundle (plan 018 AF-10). On `master` (`d1bb9b0`), the root block's `moduleResolution` is `bundler`, which Next 16.4.6 rewrites into the file on every build if it is absent. The `ts-node` block carries its own `moduleResolution`, `node`, because its `module` is `commonjs` and TypeScript refuses `bundler` with it (TS5095); `website.md` A-4's `ts-node` check and the `lang`, `push-commands` and `backfill-valid` scripts depend on that key.
- **Client navigation between two values of one dynamic segment** (for example `/message/f/A` → `/message/f/B`): the App Router keeps the previous page mounted but hidden, in one `<Activity>` entry, and mounts B's page and modal fresh. The entry's key is `name|value|type`, so a changed `[id]` is a new entry. Without `cacheComponents`, which `next.config.js` does not set, `MAX_BF_CACHE_ENTRIES` is 1. This holds at Next 16.1.6 (`layout-router.js`, `createRouterCacheKey`) and at 16.4.6 (`createSegmentKey`, whose browser variant returns `createRouterCacheKey`). Read by plan 018's implementer (M4 R6) and re-derived by the architect from both installed sources. Plan 015 X-22 rests on it.
- **Bot**: `bot/edgeCommands.ts` answered directly from the signature-verified edge endpoint; `bot/serverCommands.ts` forwarded to `interactions-server` authenticated by `HOOKS_API_TOKEN`.
- **Editor architecture** (key frontend pattern): a **single component tree** serves both editing and preview. `DiscordMessageEditor` accepts `message`, `setMessage`, `editableState`; `editableState.showEdit=true` renders Slate editors and toolbars, otherwise static read-only views. `MessagePreview` wraps it with a no-op `setMessage`. Sub-components (`DiscordContentEditor`, `EmbedEditor`, `ComponentEditor`) follow the same dual-mode pattern. A second, independent input, `hideValidation` (optional, default `false`), turns off every validation line and the accessories `errorBorder`. `DiscordMessageEditor` passes it beside `showEdit` to `Author`, the one sub-component whose line renders read-only. Only `src/app/preview/page.tsx` sets it, so preview images carry no validation chrome, while the editor and the send page's read-only `MessagePreview` keep every line (D-001).
- **Provider architecture**: every provider follows the 5-step formula — `createContext(null)`, throwing `useXxx()` consumer hook, private `useValue()` with `useMemo`, `memo()` wrapper, `displayName`. Key providers: `MessageProvider`, `GuildProvider`, `MarkdownProvider`, `WebhookProvider`.
- **Data flow**: Load: DB (JSONB) → `message.get` → `makeEditable()` → key injection → UI state. Save: UI state → `gateBeforePersist()` (and, where it must ask, the user's choice through `applyDisposition()`) → `stripKeys()` → `message.upsert` → DB, which records `valid` (below). Send: UI state → `stripKeys()` → `sendWebhook()` → Discord webhook API — issued from the browser (`src/app/message/m/[id]/send/page.tsx`, a client component), not through the website's own API; the page enables Send only when `validateMessage` returns no reason. That predicate includes `validateV2Components` (`limits.tsx`), which refuses the Components V2 shapes Discord was measured refusing, against a 120-member measured corpus (plan 016).
- **One serialiser on both write paths**: `stripKeys` (`src/utils/index.ts`) removes the editor's `_key`s and, when `data.components` carries a V2 type, ORs `IS_COMPONENTS_V2_FLAG` into `data.flags` (structure → flag, one direction). It removes no user content and never clears the bit (`website.md` W-1). Save and send both call it, so the same function decides what the DB stores and what Discord receives. `sendWebhook` (`src/utils/sendWebhook.ts`) *reads* that bit and, when set, adds `with_components=true` to the webhook URL — it applies nothing to the message. The mode toggles own the rest of the bit's life: `switchToV2` (`src/utils/messageMode.ts`) sets it and clears content and embeds; `switchToClassic` clears it.
- **The persist gate**: `gateBeforePersist` (`src/utils/index.ts`) runs `resolveContentLoss` over a draft before any user-driven save. Where saving would lose content it returns the options for the user's choice (plan 013 D17's principle, D-004); otherwise it returns the draft with embeds that are entirely empty dropped beside V2 components (`dropEmptyEmbedsBesideV2`, chain `fix-website-save-gate-embeds`). The JSON load surfaces (`JsonModalBody.tsx`, `NewMessageJsonInput.tsx`) call `resolveContentLoss` directly.
- **Persisting writers**: `api.message.upsert.useMutation` has five call sites. Three go through the gate and `stripKeys`: the editor (`providers/MessageProvider`, whose `saveMessage` and `commitSaveChoice` share one `persist` step in `useApiMethods.ts`; `website.md` A-6), `NewMessageModal.tsx` (via `saveAsPayload`) and `SaveAsMenu.tsx`. Two write a fixed classic intro message from `copyIntroMessage()` directly: `message/f/[id]/page.tsx` and `message/m/new/page.tsx`. The server boundary normalises and refuses nothing beyond the save schema's shape (D-005).
- **Validity is recorded, not enforced**: `upsertMessage` (`src/server/api/utils/shared.ts`) stores `valid: isMessageValid(message.data)` (`messageValidity.ts`, which calls `validateMessage`). The public v1 API (`src/pages/api/v1/guilds/[guildId]/messages.ts`, `…/messages/[id].ts`) serves the stored `valid` when non-null. `src/scripts/backfillValid.ts` re-derives only rows whose `valid` is NULL. ## Runtime Flows

1. **Edit/save**: browser UI state ↔ tRPC `message` router ↔ Postgres JSONB via project-utils Kysely.
1b. **Cross-tab staleness notice**: when a save updates an existing row, the server triggers a Pusher event on a per-message channel; a save that inserts (a new message, or a number the owner-scoped update matched no row for) triggers none (website `983681c`). `shared.ts` `upsertMessage` sends `JSON.stringify(hashMessage(message))` to `genMessageChannelKey(message.id)` as `message-update`. The JSON encoding is the wire contract (release tree `787bec5`; plan 017 D-33). Node `pusher` sends string data unchanged, and pusher-js's `decodeMessage` `JSON.parse`s it back to the producer's exact hex string. A bare hash that parses as a number (`5e7`, `-1e10`) would otherwise arrive as a number. Each open composer subscribes (`providers/MessageProvider/usePusher.ts`) through its own Pusher instance, created per run of the hook's effect and disconnected when that run ends: on unmount, or on a move to another message (plan 017 M2-d). It compares the delivered value by strict equality against `hashMessage(stripKeys(current))`, so a payload that is not the exact string raises the notice and never suppresses it; a mismatch raises the *"Message Update Detected"* prompt offering Reload, warning that local changes will be lost. It **flags divergence; it does not coordinate or merge** — owner-stated intent, 2026-08-24, verbatim: *"there's a `pusher` or similar service employed to try and allow some kind of coordination (or rather, flag when front-end state doesn't match back-end because of a different tab saving)"*, his own correction mid-sentence, confirmed against the tree. Producer and consumer hash the same form: the server hashes the upsert input as the save schema parsed it, and the client hashes `normalizeForHash(current)` — `stripKeys` of the draft parsed by the same `discordMessageShape` (`usePusher.ts`, plan 013 `495463a`). The saving editor is set to the data it stored (the shared `persist` step, `website.md` A-6), so the hash its own tab compares is the stored one (chain `fix-website-save-gate-embeds`, code review CR-4). The saving tab also records the hash of each save it sends (`usePusher.ts` `recordOwnSave`, called in `persist` for an existing message; `forgetOwnSave` on the mutation's error). A broadcast that matches a record consumes it and raises nothing in that tab, so an edit typed while the save is in flight does not prompt the saver. Other tabs hold no record and compare as before (plan 017 M2).
2. **Send**: UI state → `stripKeys()`, which applies `IS_COMPONENTS_V2_FLAG` when V2 components are present → `sendWebhook()` → Discord webhook API, called from the browser. `sendWebhook` reads the bit to set `with_components=true` on the URL; it does not set the bit.
3. **Preview image (write)**, at website `983681c` and generator `8512a1d`, both in production: `message.upsert` commits the row and replies → `waitUntil` runs the continuation → POST `/generate` `{ id, nonce, message }` → puppeteer renders website `/preview` → JPEG → DigitalOcean Spaces bucket `hooks` at `[dev/]previews/{id}/{nonce}.jpeg` (public-read) → 204 → the website commits `previewImageNonce` if the new nonce sorts above the stored one → the website deletes the replaced object and sweeps objects 120 s older than the committed one, or deletes its own object if the commit was refused. Any answer but 204, or none within 40 s, leaves the row and the bucket as they were (the stale preview stays) and writes a `preview-image-failure` line on each side that saw it. The generator only writes; listing and deleting are the website's, here and in `deleteMessagePreviewImages.ts` on a message delete (a table-era name for a bucket operation).
4. **Preview image (read)**: the website emits `https://cdn.hooks.gg/previews/{id}/{nonce}.jpeg` (`getCDNUrl()` + `NEXT_PUBLIC_CDN_HOST`); `cdn.hooks.gg` is a CNAME to the Spaces CDN edge (`hooks.nyc3.cdn.digitaloceanspaces.com`, Cloudflare-proxied), so the request is served straight from the bucket object PIG wrote.
5. **Bot interaction**: Discord → `POST /api/interactions-edge` (signature verify) → edge commands answered inline; server commands forwarded to `/api/interactions-server` (`HOOKS_API_TOKEN`) → DB/Redis.
6. **Cron**: daily `/api/cron?key=vercel` per `vercel.json`.

## Decisions

### D-001 — Single component tree for edit and preview
- **Context**: WYSIWYG fidelity requires the preview to be pixel-true to the editor.
- **Choice**: One `DiscordMessageEditor` tree, mode-switched by `editableState.showEdit`.
- **Consequences**: No drift between edit and preview rendering; every sub-component must implement both modes. Reused by the screenshot pipeline (the `/preview` route renders the same tree). Validation chrome is a second axis, not a mode: `hideValidation` on `VisualizerProps`, set only by `/preview`, drilled as a prop beside `showEdit`. It is not keyed on edit mode, because the send page's read-only render needs the lines. It is not a context, so the tree keeps one route for mode-like inputs. It is not CSS, so it keys on validation and not on styling (plan 016 D-14, his selection 23; AF-13). A validator added to the tree reads it at its render site.
- **Standing**: **confirmed inference**, not owner-authored — put to the owner 2026-08-24, who answered *"Agent's inference is correct."* It is only as strong as the inference he was shown; re-verify the mechanism, not the agreement. See `website.md` W-3.
- **Related**: Plans 001, 004.

### D-002 — Shared data layer as a git-dependency package with committed dist
- **Context**: Multiple deployables (website, and at the time cdn) needed one schema and one connection discipline.
- **Choice**: `project-utils` owns `schema.prisma`, generates Kysely types via prisma-kysely, exports a `getPostgres()` singleton, and is consumed as `github:hooks-gg/project-utils#master` with `dist/` committed. Owner-stated rationale (2026-08-23, verbatim): *"Same architecture as Statbot. To put it shortly; api-extractor."* — a git dependency has no publish step; the committed `dist/` plus the API Extractor `.d.ts` rollup are what make the repo installable as-is.
- **Verification**: `project-utils` and statbot's `statbot-utils` carry an identical `build:types` script (`tsc -p ./tsconfig.json --declaration true --outDir build/types && api-extractor run`), both hold an `api-extractor.json`, and both track `dist/` in git (13 and 264 files respectively).
- **Consequences**: No registry publishing needed; consumers pin `#master`, so a project-utils push changes consumers on next install; committed build artifacts must be kept in sync by the pre-commit hook — and must never be "cleaned up" as if they were stray build output.
- **Related**: statbot workspace (`statbot-utils`), which this deliberately mirrors.

### D-003 — Preview images by screenshotting the app's own preview route
- **Context**: Preview images must match what the editor shows (see D-001).
- **Choice** (owner-sourced 2026-08-24, verbatim): *"That's the only way I figured how to do it: to render an exact representation of the message in the browser, one had to load and snapshot it in the browser. If there are other ways, I just did not know of them."* A separate puppeteer service renders the website's `/preview` page and uploads JPEGs to public S3 rather than re-implementing rendering server-side.
- **Standing**: this is a **route he knew**, not a trade-off he weighed — unlike D-002, whose rationale he authored. The durable requirement is *an exact representation of the message*; puppeteer is the implementation that requirement could reach. A better route is what this decision was waiting for, not a violation of it. The bar for proposing one is now stated: a demonstration of what "close enough" actually looks like, his current valuation being that the setup works and costs are immaterial (`preview-image-generator.md` P-1, conditional on those facts holding). See `website.md` W-4.
- **Consequences**: Zero rendering drift; adds a headless-browser service and an S3/CDN dependency; the service is coupled to the website's `/preview` URL contract (message JSON in a query param).

### D-005 — The back end reflects what the front end allows
- **Context**: Three of five `message.upsert` call sites bypass the `stripKeys` serialiser, and the tRPC boundary neither normalises nor rejects. This architect registered that in 2026-08-24 as a missing boundary enforcement, and asked the owner whether `message.upsert` should refuse an unserialised message.
- **Choice** (owner ruling, 2026-08-24, verbatim): *"A message is allowed to be saved in a bad state (e.g., missing content, over character limits, etc.) … I'd say that the back-end reflects what the front-end allows. If a shape is allowed in the front-end, then it's not silently morphed in the back-end. If there's a question of what's allowed in the front-end, that's the question to ask. (We're talking strictly about saving the message as it's being edited.)"* Persisting an invalid draft is intended: validity is recorded (chain 012's `valid` column), never enforced at the write boundary. The back end stores the shape the front end permitted, unaltered. Where a shape should not be storable, the answer is to settle what the front end allows — not to add a server-side gate.
- **Alternatives**: *Gate `message.upsert` on `validateMessage`* — proposed by this architect and excluded by the ruling: it would refuse the bad-state saves the owner says are allowed. *Normalise server-side* — excluded by the same words, as silent morphing.
- **Consequences**: The serialiser must not delete user content on its way to the DB, which is the architectural ground for D18/M8-G (chain 013): `stripKeys`' output is its input modulo `_key`s plus the V2 bit, and the block-and-ask for a lossy save lives at the front-end writers. The residual debt is front-end cohesion — writers sharing a criterion rather than a path (see Problem Areas) — and is not resolvable by anything at the boundary. The owner scoped this ruling to *saving a message as it is being edited*; it does not speak to the import surfaces, whose disposition is D-004's five rows.
- **Related**: D-004; plan 013 (D18, M8-G); chain 012's `valid` column, which is the recording mechanism this decision relies on instead of enforcement.

### D-004 — The flag is the mode
- **Context**: A Discord message is Components V2 by carrying `IS_COMPONENTS_V2_FLAG` (32768, `1 << 15`). The website had no single answer to "what makes a message V2": the send gate reads the bit, the composer and the importers read the components. Discord itself can send a V2-marked message whose top-level components are all Action Rows — a shape with the marking and no V2 structure — which under a structure-only rule opens in Classic with nothing showing the marking.
- **Choice** (owner ruling, 2026-08-24, verbatim): *"If it has the flag, then it's V2. If it's V2 and there are conflicts in the body, there's an error mesage."* [sic] A message is Components V2 iff its `flags` carry `IS_COMPONENTS_V2_FLAG` **or** its components include a V2 type — the predicate `validateContentRequirements` already uses — and the composer shows V2 for every such message. The flag is an input that decides V2-ness, not an output read back from structure. A V2 message whose body carries content or embeds is the conflict: a stored record in that state shows the composer's error. At the two JSON submission surfaces the disposition is not that predicate but a five-row table over the cell (V2 bit, V2 components, classic body), ruled 2026-08-24 as D17 under the owner's governing principle — *"fail gracefully when no content will be lost. If content must be lost to fulfill the request, block, notify, and present the user with a choice."* A bit standing over a classic body is warned and cleared, keeping the body; V2 components together with a body put the choice to the user. Nothing is dropped silently, and nothing is refused. On save, `stripKeys` sets the bit whenever V2 components are present (structure → flag, one direction) and never clears it; the toggle to V2 sets it and the toggle to Classic clears it, so the bit and the mode shown never disagree within a session.
- **Alternatives**: *Mode derived from structure, the flag an output only* — the premise every document in this line held until 2026-08-24, resting on `detectMode` reading `hasV2Components` alone; withdrawn by the owner. It cannot represent a marked message with no V2 structure, and it makes the send gate and the composer disagree about the same record. *Normalise the bit on every save-path writer* — was in front of the owner and not taken; it would repair records silently rather than surfacing the conflict.
- **Consequences**: The bit becomes load-bearing data, so every writer that reaches `message.upsert` must produce it correctly — which the current call-site convention does not guarantee (see Problem Areas). Three surfaces state the withdrawn premise in code today: `detectMode` and `enforceImportMutualExclusivity` must move to the flag-or-structure predicate, and `switchToV2` must set the bit its counterpart already clears. Behaviour changes for existing stored records: a message carrying the bit over Action Rows only, or over no components, now opens in V2. The bit standing over such a message is not a conflict and is not refused — only the bit together with content or embeds is.
- **Related**: Plan 013 (Decisions Register D15 and D17, with D11/D13/D16 bounding the conflict class and the toggle); plan 012's V2 data-layer work; research `8311155a`, whose "flags derive from structure" clause this supersedes. Two premises were withdrawn on the way here and neither survives in this decision: that mode derives from structure (withdrawn at D15), and that a conflicting submission is refused at import (D5 option (a), withdrawn at D17).

### D-006 — The preview outcome is handled after the save replies, through `@vercel/functions` `waitUntil`
- **Context**: His intent on a failed generation is *"Show a stale one is fine"* (`preview-image-generator.md` P-6). The save must not wait on the render (plan 017 hazard 3, from his answer). To keep the last good image, the website must learn the generator's outcome before it moves `previewImageNonce`, and that outcome arrives after the save has replied. The save runs in a Pages Router tRPC route, where Next's `after()` throws (plan 017 AN-3, verified locally at Next 16.1.6). The project's functions run with a 60 s limit (plan 017 D-10, read from the project settings).
- **Choice**: the website adds `@vercel/functions`, pinned exactly at `3.11.3`, and passes `runPreviewContinuation` to `waitUntil` from `upsertMessage` (`shared.ts`). The continuation bounds its generator wait at T = 40 s. T is set from the render-time distribution (p99 3729 ms, max 26275 ms; plan 017 AN-4), so a save's own work (up to 15 s) plus T stays inside the limit. It was gated before any M5 code by two probes on Preview deployments: post-response work kept alive (`deployment/` record `d61f445`) and lasting to 55 s (`8f26f37`), both pushed on his approval (plan 017 D-27, D-30). The commit is conditional on nonce order, so continuations that finish out of order cannot move the row backwards. An agent-designed mechanism; his selections approved the probes, not the design.
- **Alternatives**: *Await the generator inside the save*: it trades away "the save never blocks and never slows". *A stable key per message, overwritten in place* (plan 017 AF-8, recorded beside M5-0's fallback): no commit protocol, no deletion transfer and no runtime gate. It rests on the CDN's query-string cache key and a migration of legacy keys, neither of which was read, and it moves his D-8 line. *A queue or cron sweep outside the save*: new infrastructure for what one continuation does.
- **Consequences**: The website, not the generator, owns deletion, so the generator's key needs no list or delete rights (security audit 017 I-1). Correctness depends on a platform lifetime: if Vercel cuts post-response work earlier, or the project's limit drops below 55 s, previews go stale and orphan objects grow, but no image breaks (Problem Areas, the orphan-object row). The `preview-image-failure` `no-answer-within-T` count is the signal. The production limit for post-response work is Inference from documentation and was measured on a Preview only. A change to the function settings reopens D-10's read. The dependency is the one place the website couples to Vercel in code. A move off Vercel needs a substitute for `waitUntil` (the record's Quality Attributes: the website deploys on Vercel by his 2026-08-23 ruling).
- **Related**: plan 017 M5, M5-0, M6, D-8, D-10, D-27, D-30, AF-8, RK-2; D-003; Runtime Flow 3.
